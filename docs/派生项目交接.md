# 派生项目交接

这是派生站的交接、验证和正式上线清单。任何一层通过都不能自动替代下一层。

## 派生边界

- 会跟随：Git 中已跟踪的代码、测试、docs、`AGENTS.md` / `CLAUDE.md`、`.claude/rules/**`、workflows 和示例配置。
- 不会跟随：真实密钥、provider 资源、部署记录、DNS、GitHub ruleset 和 branch protection。
- AI 的通用工作方法使用全局 skills；项目独有事实只写在代码、docs、`AGENTS.md` 和 rules 中。
- 本清单在每个派生项目中重新开始，不继承模板或另一站点的绿灯。

## 第一轮替换

- 仓库和所有权：remote、默认分支、workflow 权限、Cloudflare 项目和负责人。
- 业务真相：`src/config/single-site*.ts`、`src/config/public-trust.ts`、`src/config/offerings.ts`、`src/content/pages/**`、`messages/**` 和真实 offering 页面。
- 品牌和法务：域名、联系方式、logo / favicon / OG 资产、主题、Privacy、Terms 和对外声明。
- 询盘和部署：按 `.env.example` 重新配置 Turnstile、rate limit、Airtable、Resend 和 Cloudflare Secrets，不复制真实凭据。
- 文档和规则：只保留当前项目真实存在的路径、命令和运行链。

`docs/OpenNext Draft适配器.md` 和 `docs/TypeScript 7双轨迁移.md` 只在相同 pin、补丁或双轨方案仍存在时保留。

## 验证分层

| 层级 | 证明什么 | 不证明什么 |
| --- | --- | --- |
| 本地检查 | 改动相关的类型、lint、测试和必要构建 | 不证明部署或真实 provider |
| PR CI | GitHub runner 上的完整工程检查 | 不证明正式域名或 owner 收件 |
| `pnpm release:verify` | 当前 SHA 的本地 release 技术序列 | 不部署，不证明正式上线 |
| deployed smoke | 本次 Worker URL 的核心 GET 路由 | 不证明 DNS、TLS、Airtable 或 Resend |
| 真实业务验证 | Airtable canary、Resend 状态和 owner inbox receipt | 三份证据不能互相替代 |

Next build、Cloudflare/OpenNext build 和 Playwright webServer 共用 `.next`，必须串行。真实 Airtable canary 使用：

```bash
PLAYWRIGHT_BASE_URL="$DEPLOYED_BASE_URL" pnpm canary:airtable
```

## Owner 与上线清单

- [ ] 决定 Airtable 使用低频人工复核，还是为“邮件失败但 Airtable 成功”的记录配置自动提醒。
- [ ] 配置真实 Airtable base、table 和 PAT。
- [ ] 配置真实 Resend API key、发件域名和 owner 收件邮箱。
- [ ] 真实部署后运行 Airtable canary，并核对 API 响应与 Airtable 记录使用同一 `referenceId`。
- [ ] 单独确认 Resend provider 状态和 owner 收件箱实际收件。
- [ ] 人工确认正式域名、DNS、TLS 和 Cloudflare custom domain。
- [ ] Owner 确认联系信息、法务文本、品牌内容和最终上线。
- [ ] 按实际协作需要配置 main branch protection；未配置时只能记录“未强制”。

前七项及各层工程证明全部满足后，才能称为正式上线。第八项是按协作需要启用的仓库治理。缺少任何必需证据时，只能记录“部分证明”或“未证实”。
