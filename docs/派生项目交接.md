# 派生项目交接

这是派生站的交接、验证和正式上线清单。模板默认保留首页、联系和法务页面骨架；产品、服务与关于页由派生站按真实需求建立。任何一层通过都不能自动替代下一层。

## 派生边界

- 会跟随：Git 中已跟踪的代码、测试、docs、`AGENTS.md` / `CLAUDE.md`、`.claude/rules/**`、workflows 和示例配置。
- 不会跟随：真实密钥、provider 资源、部署记录、DNS、GitHub Environment 及其部署分支策略、GitHub ruleset 和 branch protection。
- AI 的通用工作方法使用全局 skills；项目事实遵循 [内容规则](../.claude/rules/content.md) 的编写入口，docs 解释使用与交接，rules 约束改动，不在多处独立维护同一个值或状态。
- 本清单在每个派生项目中重新开始，不继承模板或另一站点的绿灯。

## 第一轮替换

按阶段使用本清单，不把上线配置变成本地设计前置条件：

- 本地设计：按 README 启动即可，服务密钥可留空，公司资料可省略；明确当前页面任务，事实未确认时先做结构草案。
- 询盘验证：使用隔离测试配置与模拟出站服务；验证真实交付时，另行准备自己的服务资源并取得外部写入授权。模拟通过不等于真实收件。
- 生产上线：完成下列业务替换、域名、法务、资源与安全配置，以及文末 Owner 清单；当前双通道交付要求不变。

下列条目是派生至上线的核对范围，不要求在开始设计前一次完成。

- 仓库和所有权：remote、默认分支、workflow 权限、Cloudflare 项目和负责人。
- 业务真相：`src/config/single-site.ts` 的 `SINGLE_SITE_CONFIG`（站点名、公司、联系方式、社交链接和品牌资产的唯一配置）、其余 `src/config/single-site*.ts`、`src/content/pages/**`、`messages/**` 和派生项目新增的真实 offering 页面。根据真实业务决定是否需要产品目录及应用场景、规格、交付边界等信息；示例填写说明不能作为上线内容。
- 多语言交接：明确默认语言、目标语言/地区、URL 方案和每种语言的内容 owner；非默认语言必须有独立 URL、完整正文、页面级 SEO、`hreflang`/canonical 对应关系和可复核的翻译来源。不能把机器翻译占位页、IP 自动跳转或同 URL 多语言内容当作已完成。
- 品牌和法务：域名、联系方式、favicon / OG 资产及可选 logo、主题、Privacy、Terms 和对外声明。`public/opengraph-image.png` 是模板图，需要换成派生站自己的分享图。
- 换主色：选一个品牌基色，用 [Radix 自定义配色工具](https://www.radix-ui.com/colors/custom) 分别生成浅色和深色的 12 阶 accent 与 gray 色阶，把 1–12 阶实色值（不含 alpha 阶）贴进 `src/app/theme.css` 的 `--brand-1`…`--brand-12` 和 `--neutral-1`…`--neutral-12`（`:root` 与 `.dark` 各一套），语义映射不用改。贴完运行 `pnpm exec vitest run tests/architecture/design-token-contract.test.ts` 核对对比度；黄、琥珀、橙等亮色常需把第 11 阶调深才能通过。最后按 `src/config/static-theme-colors.ts` 注释里的阶对应关系，用浅色色阶的 hex 刷新询盘通知邮件的 sRGB 快照。
- 询盘和部署：按下文“服务与密钥配置”重新配置 Turnstile、限流、Airtable、Resend 和 Cloudflare，不复制真实凭据。`wrangler.jsonc` 的 `env.production.vars.TURNSTILE_ALLOWED_HOSTS` 必须显式填写逗号分隔的 hostname 列表，包含同处 `NEXT_PUBLIC_SITE_URL` 的 hostname，且不得含占位值或本地域名；缺失、空白或空列表不能通过严格上线门禁，不能依赖运行时 fallback 代替此配置。严格上线门禁同样拒绝格式不合法的 `EMAIL_FROM`（接受裸地址或 `Name <address>`）、`INQUIRY_RECIPIENT_EMAIL` 和 `LOG_LEVEL`，以及 `.env.production`、`public/.well-known/security.txt`（含过期的 `Expires`）、`messages/base/**`、`src/content/pages/**` 和 production Turnstile site key 中仍保留的模板占位内容。它还拒绝 Cloudflare 官方 Turnstile 测试 site key/secret、production 变量里的 `NODE_ENV=development|test` 与 `TURNSTILE_BYPASS=true`、没有可用 `Contact`（真实域名的 `mailto:` 或 `https:`）的 `security.txt`，以及 IP 字面量或单标签主机的公开 URL；具体规则以 `scripts/quality/checks/production-config.js` 为准；在本地运行 `PUBLIC_LAUNCH_STRICT=true APP_ENV=production node scripts/quality/checks/production-config.js` 可一次列出全部剩余占位项。
- 生产部署环境：在 GitHub 建 `production` Environment，部署分支限定为 `main`；生产 secrets 只放进该环境的 secrets，不放仓库级。仓库级 secret 对任何分支上的任何 workflow 都可见，Environment 的“只允许 main”策略管不到它们。
- 文案收尾：上线前通读 `messages/**`、`src/content/pages/**` 和页面 metadata，删掉当装饰用的中点“·”分隔符，以及渲染在页面上的解释性填充语（例如说明区块用途或写给编辑者看的话）。
- 模板专属设置：见下文“模板专属设置清单”，逐项决定保留、改写或删除。
- 文档和规则：只保留当前项目真实存在的路径、命令和运行链。

需要外部研究时，将原始资料留在研究工作区；仓库只接收相关的已批准内容和未证明边界。不要求每次派生新建研究工作区，也不继承其他站点的 provider 证据。

### 服务与密钥配置

下表的值都按派生站自己的资源重新创建。“GitHub production secret”指 `production` Environment 的 secret；“Worker secret”用 `wrangler secret put <名称> --env production` 写入。部署 workflow 的严格上线门禁读取 GitHub 副本，“Worker production secret 名称齐备”一步只核对 Worker 上名称存在，不核对值，所以两处要填同一个值。

| 名称 | 放在哪里 | 说明 |
| --- | --- | --- |
| `CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID` | GitHub production secret | 部署和读取 Worker secret 名称用。令牌在 Cloudflare 控制台用 “Edit Cloudflare Workers” 模板创建，账户范围限定为本站账户；绑定正式域名时把对应 zone 加入范围。账户 ID 在 Workers 概览页右侧。 |
| `TURNSTILE_SECRET_KEY` | GitHub production secret + Worker secret | 见下文“Turnstile 密钥分层”。 |
| `RESEND_API_KEY`、`EMAIL_FROM`、`INQUIRY_RECIPIENT_EMAIL` | GitHub production secret + Worker secret | `EMAIL_FROM` 的域名须先在 Resend 验证；见下文“域名邮箱”。 |
| `AIRTABLE_API_KEY`、`AIRTABLE_BASE_ID` | GitHub production secret + Worker secret | Worker 写入只需本 base 的 `data.records:write`；本机运行 Airtable canary 时用的 PAT 还要 `data.records:read`（按邮箱查回并删除测试记录）。base ID 是 base URL 中 `app` 开头的一段。表结构见“Airtable Contacts 表列”。 |
| `AIRTABLE_TABLE_NAME` | `wrangler.jsonc` 的 `env.production.vars` | 可选，缺省为 `Contacts`。生产部署不带 `--keep-vars`，在 Cloudflare 面板手动设置的普通变量会在下次部署时被清空，所以只能写在 `wrangler.jsonc`。 |
| `UPSTASH_REDIS_REST_URL`、`UPSTASH_REDIS_REST_TOKEN` | GitHub production secret + Worker secret | 在 Upstash 控制台建一个 Redis 数据库，从 REST API 区块复制 URL 和 token。生产必需：缺失时严格门禁阻断。 |
| `RATE_LIMIT_PEPPER` | GitHub production secret + Worker secret | 限流 key 的 HMAC 密钥，至少 32 个字符，例如 `openssl rand -base64 48` 生成。 |
| `NEXT_PUBLIC_SITE_URL`、`NEXT_PUBLIC_BASE_URL`、`NEXT_PUBLIC_TURNSTILE_SITE_KEY`、`TURNSTILE_ALLOWED_HOSTS` 等公开配置 | `wrangler.jsonc` 的 `env.production.vars` | 部署 workflow 从这里导出构建环境，缺失会阻断。 |
| `NEXT_PUBLIC_GA_MEASUREMENT_ID`、`GOOGLE_SITE_VERIFICATION`、`BING_SITE_VERIFICATION` | GitHub Actions variables（可选） | 公开值，构建时读取；workflow 先读 variables，再回退到同名 secret。留空即不输出对应验证 meta。GA 只在访客于 Cookie 横幅允许分析或广告至少一类后加载，并按 Google Consent Mode v2 发送同意状态：分析对应 `analytics_storage`，广告对应 `ad_storage`、`ad_user_data`、`ad_personalization`，默认均为 denied，撤回时同步更新，并清除本站已写入的 `_ga`、`_ga_<ID>` cookie。 |
| `CLOUDFLARE_PREVIEW_URL` | GitHub Actions variables | 派生站真实 preview Worker 的 https URL。CI 的 Cloudflare 构建用它作为站点 URL；不设置时回退到 `https://example.invalid`。 |

Preview Worker 用同样的名称，以 `wrangler secret put <名称> --env preview` 写入；preview 发布带 `--keep-vars`，会保留这些值。

preview 和 production 不要共用 Upstash 数据库或 Airtable base/表：canary 和测试提交会混进正式备份表，preview 上的测试也会消耗同一份配额。限流 key 已按 `APP_ENV` 加前缀，即使误用同一个数据库，两边的计数也不会互相影响，但仍应分开建。

Airtable 备份是必选项，不能只保留邮件：它是邮件之外防丢询盘的第二通道，严格上线门禁、部署 workflow 的 Worker secret 检查和 release 验证都要求它；“只发邮件”不是模板支持的配置。

### Turnstile 密钥分层

派生站必须在自己的 Cloudflare 账户为正式域名创建独立的 Turnstile widget，不沿用模板或其他站点的 key；`wrangler.jsonc` 中现有的 site key 是模板值，必须替换。

- 公开 site key：`NEXT_PUBLIC_TURNSTILE_SITE_KEY`。本地写入 `.env.local`；生产写入 `wrangler.jsonc` 的 `env.production.vars`（部署 workflow 从这里读取，缺失会阻断）。
- 私密 secret key：`TURNSTILE_SECRET_KEY`。本地配置见 [README 的快速开始](../README.md#快速开始)；生产值放在 GitHub `production` Environment 的 secrets（严格上线门禁读取）和 Worker secret（`wrangler secret put TURNSTILE_SECRET_KEY --env production`；部署前会核对该名称存在），真实 secret 不写入 [环境变量示例](../.env.example)、`wrangler.jsonc` 或 Git。
- 只配置前端 site key 不等于防护生效；服务端校验、hostname 白名单（`TURNSTILE_ALLOWED_HOSTS`，见上文“询盘和部署”）和 secret 缺一不可。hostname 不匹配的失败对买家表现为普通反滥用拒绝，需在服务端日志中看 `invalid-hostname`（见 [安全规则](../.claude/rules/security.md)）。

### 域名邮箱

B2B 买家通常期待官方域名邮箱（如 `sales@yourdomain.com`）。可选做法是用 Cloudflare Email Routing 把域名地址转发到负责人邮箱，并在其邮箱服务中配置以该域名地址发信；具体步骤以所用邮箱服务的官方文档为准。

网站询盘提交后的 owner 通知邮件仍由 Resend 发送（`EMAIL_FROM`、`INQUIRY_RECIPIENT_EMAIL`，`Reply-To` 为买家邮箱）；域名邮箱只负责买家主动来信的接收和人工回信，两者要分别验证。

### 旧站网址跳转

替换已有网站时，旧网址要永久跳到新地址，否则搜索排名和外链会丢失。在 `next.config.ts` 的 `redirects()` 返回数组里，接在默认语言前缀的两条规则后面追加，例如 `{ source: "/products.html", destination: "/products", permanent: true }`。`permanent: true` 返回 308，搜索引擎按永久跳转处理；确需 301 时用 `statusCode: 301` 代替 `permanent`（两者不能同时写）。这些规则先于 middleware 执行，旧路径不需要在页面注册表登记。上线后逐条用 `curl -sI https://<正式域名>/products.html` 验证：状态码为 308（或 301），`Location` 指向新地址，再确认新地址本身返回 200。

## 设计与内容继承边界

默认继承：页面阅读逻辑、排版层级、间距节奏、组件边界、询盘路径、无障碍、性能和审查方式。不预设产品模型、七类采购区块或品牌颜色。设计规则见 [设计真相](design/设计真相.md)，代码实现规则见 [UI 实现规则](../.claude/rules/ui.md)。

公开上线前必须配置：品牌、域名、真实公开邮箱、法务、SEO 内容和地区语言。公司、电话、地址、成立年份、社交链接和 logo 可以省略，留空即不展示、不进结构化数据；填写的值会原样上线，必须有效且无占位值：格式在 `SINGLE_SITE_CONFIG` 加载时校验（格式错误会让 `pnpm build` 失败），占位值只由严格上线门禁（`scripts/quality/checks/production-config.js`）拦截，运行时不再猜测。需要产品内容的派生站再补充真实产品事实、应用场景、规格、材料、交付边界和证据。

页面结构和视觉是推荐默认，不是不可变契约。业务事实、品牌定位或用户反馈支持变更时，可以调整；必须保留内容真实性、安全、可访问性和询盘交付能力，并验证受影响行为。

## 验证分层

本地、CI 与发布检查的触发方式统一见[质量门禁](质量门禁.md)；本节说明派生站必须重新取得的工程与业务证明。

### 工程与业务证明

| 层级 | 证明什么 | 不证明什么 |
| --- | --- | --- |
| 本地检查 | 改动相关的类型、lint、测试和必要构建 | 不证明部署或真实 provider |
| PR CI | GitHub runner 上的完整工程检查 | 不证明正式域名或 owner 收件 |
| `pnpm release:verify` | 当前 SHA 的本地 release 技术序列 | 不部署，不证明正式上线 |
| deployed smoke | 本次部署的 workers.dev URL（配置 routes/custom_domain 后 workers.dev 关闭，改为 `NEXT_PUBLIC_SITE_URL`）的核心 GET 路由，以及向 `/api/inquiry` 发送 `Content-Type: text/plain` 的 POST 并期望 415；该探测在来源检查和限流前返回，无副作用、不调用服务商，只证明询盘路由模块能加载并响应 | 不证明 Worker secrets、来源检查分支、真实询盘投递、正式域名的 DNS/TLS、Airtable 或 Resend |
| 真实业务验证 | Airtable canary、Resend 状态和 owner inbox receipt | 三份证据不能互相替代 |

### 浏览器验证继承

派生项目继承模板的测试分工：固定、可重复的用户流程使用仓库中的
Playwright 测试；Agent 可用于探索未知 UI 问题、视觉检查和建立复现步骤。
探索出的稳定问题，若具有回归价值，应固化为 Playwright 用例。不要求所有改动
都新增 E2E，应优先使用能直接证明契约的最窄测试。

派生项目必须重新确认 `baseURL`、服务启动命令、测试数据、认证方式和外部
provider 边界。模板项目的 CI 通过不继承为派生项目的通过，派生项目必须在
自己的提交和环境中重新运行并记录证据。

多语言派生还要逐语言核对：公开 URL、`<html lang>`、正文语言、页面标题/H1、自指向 canonical、双向 `hreflang`、sitemap alternate、语言切换链接和非法 locale 的 404。搜索平台验证（Google Search Console、Bing Webmaster、Naver Search Advisor 等）属于外部平台证据，不由本地 build 或 `release:verify` 代替。

Next build、Cloudflare/OpenNext build 和 Playwright webServer 共用 `.next`，必须串行。真实 Airtable canary 使用：

```bash
PLAYWRIGHT_BASE_URL="$DEPLOYED_BASE_URL" pnpm canary:airtable
```

## Airtable Contacts 表列

写入的列名取自 `src/lib/airtable/service-internal/lead-records.ts`，列名必须逐字一致（区分大小写）。Airtable 对不存在的列返回 422 `UNKNOWN_FIELD_NAME`，整条记录写入失败；买家侧成功提示不能证明备份成功，交付语义见 [安全规则的 Lead-family behavior](../.claude/rules/security.md#lead-family-behavior)。排查时查看服务器错误日志：响应体中的 `error.type` 符合大写字母及下划线格式且长度为 1–64 时，会记录为 `airtableErrorType`；不记录 provider 的错误消息或完整响应体。

| 列 | 何时写入 |
| --- | --- |
| `Email`、`Submitted At`、`Status`（值 `New`）、`Source`（值 `Website Inquiry`）、`First Name`、`Last Name`、`Message` | 每条询盘都写 |
| `Reference ID` | 每条询盘都写；适配器输入必须携带引用号 |
| `Requirements` | 买家填写了需求描述时写 |
| `UTM Source`、`UTM Medium`、`UTM Campaign`、`UTM Term`、`UTM Content`、`Landing Page`、`Captured At` | 提交数据中对应值非空时写；浏览器归因来自当前会话首次保存的有效 UTM 或 `gclid` 访问（见 `src/lib/marketing/utm.ts`；`gclid` 和买家语言只进业主邮件，不写 Airtable），所以提交页本身不带 UTM 也可能写入。没有归因数据的询盘不会触发这些列，缺列也不会在这类测试中暴露 |

`Status` 和 `Source` 若建为单选列，必须预先包含上述取值。表里可以有代码不写入的其他列（例如 Company、Product Name、GCLID），它们不影响写入。Airtable canary 会带全部五个 UTM 参数访问 `/contact`，并断言上述归因列写入了记录，用它验证建表时没有漏列。

## 模板收集的数据

下表只列模板代码实际收集的数据和去向，供 owner 或律师写真实的隐私政策；模板不提供法律文本。派生站新增字段、服务商或脚本时须同步更新隐私政策。

| 数据 | 来源 | 去向 |
| --- | --- | --- |
| 姓名、邮箱、留言 | 询盘表单 | Resend 发给 owner 收件邮箱（买家邮箱作 `Reply-To`）；Airtable 备份 |
| UTM 参数（source、medium、campaign、term、content）、落地页、捕获时间 | 带 UTM 参数或 `gclid` 进站时记录，随询盘提交 | owner 邮件的 Attribution 区块；Airtable 备份（见上文“Airtable Contacts 表列”） |
| Google Ads 点击 ID（`gclid`） | 与 UTM 一起记录，随询盘提交 | 只进 owner 邮件的 Attribution 区块，不写 Airtable |
| 买家使用的页面语言 | 询盘表单提交时附带当前页面 locale | 只进 owner 邮件（Language 一行），不写 Airtable |
| 访客 IP | 提交询盘的请求 | Cloudflare Turnstile 服务端校验（`remoteip`）；Upstash Redis 只存 IP 经 `RATE_LIMIT_PEPPER` HMAC 后的截断值，作为限流计数键，窗口结束后过期 |
| Turnstile 人机验证 | 表单页加载的 Cloudflare Turnstile 小组件 | Cloudflare |
| Google Analytics 统计 | 只在设置 `NEXT_PUBLIC_GA_MEASUREMENT_ID` 且访客同意后加载 gtag；同意后点击邮箱、电话、WhatsApp 链接会上报 `contact_click` 事件，只带渠道，不带地址或号码 | Google；GA 自身的 cookie 由 Google 脚本写入 |
| `sessionStorage` 的 `inquiry-draft` | 表单草稿（姓名、邮箱、留言），提交成功后清除 | 只留在访客浏览器 |
| `sessionStorage` 的 `inquiry_attribution` | 当前会话首次有效的 UTM 或 `gclid` 访问 | 只留在访客浏览器，提交时随询盘发送 |
| `localStorage` 的 `cookie-consent` | 访客的 cookie 同意选择 | 只留在访客浏览器 |

托管、日志和链路追踪由 Cloudflare Workers 承担（见下文 Workers observability 计费一项）。

## Owner 与上线清单

部署前由负责人记录当前可用提交和 Cloudflare 部署版本。现有 workflow 在部署后的 smoke 失败时会报错，**不会自动撤回已发布版本**；不能把失败标记当成已经恢复。
如发布后异常，先停止继续发布，再由有权限的负责人使用 Cloudflare 原生版本恢复能力或重新发布已验证版本，随后复核 Worker、正式域名和询盘服务。
代码恢复不能自动恢复 secrets、DNS、外部服务数据或缓存状态；有相应变更时必须分别核对。模板审查不实际执行生产回滚，上线负责人须在自己的环境验证恢复方式。

- [ ] 指定 Airtable 备份收件箱的复核负责人和周期；按引用号核对未处理询盘，不能只检查带邮件失败标记的记录。
- [ ] 配置真实 Airtable base、table 和 PAT，并按上文“Airtable Contacts 表列”建好全部列。
- [ ] 配置真实 Resend API key、发件域名和 owner 收件邮箱。
- [ ] 真实部署后运行 Airtable canary，并核对 API 响应与 Airtable 记录使用同一 `referenceId`。
- [ ] 单独确认 Resend provider 状态和 owner 收件箱实际收件。
- [ ] 确认 Turnstile widget 绑定的是正式域名，并用真实提交确认服务端校验通过（日志无 `invalid-hostname`）。
- [ ] 若使用域名邮箱，验证买家来信能转发到负责人邮箱，且人工回复使用的是域名地址。
- [ ] 人工确认正式域名、DNS、TLS 和 Cloudflare custom domain。
- [ ] 在 Google Search Console 验证正式域名（设置 `GOOGLE_SITE_VERIFICATION` 后重新部署，或用 DNS 验证），并提交 `/sitemap.xml`。
- [ ] 在 Bing Webmaster Tools 验证站点：可直接从 Google Search Console 导入，或把 Bing 提供的 `msvalidate.01` 验证码设为 `BING_SITE_VERIFICATION` 后重新部署。
- [ ] 在 GA4 把询盘成功后上报的 `generate_lead` 事件标记为关键事件（key event）。
- [ ] 检查 Cloudflare 的 AI 爬虫设置，确保 ChatGPT、Claude、Perplexity 等 AI 回答引擎能抓取。新 zone 的默认值在 Cloudflare 文档中说法不一，一律读取本 zone 的实际设置，不按默认值推断：
  - Security → Settings → Bot traffic →“Configure AI bot policies”：Search 和 Agent 设为 Allow；Training 设为 Allow 或 Disallow AI Training，不用 Block 或 Block on pages with ads，这两项现在也会拦截 Googlebot、Bingbot 和 Applebot（[说明](https://blog.cloudflare.com/accountable-mixed-use-ai-crawlers/)）。旧版 “Block AI bots” 开关如仍显示，设为不屏蔽。
  - Bot Preference Sync 对新客户默认开启，会把 Cloudflare 托管规则加在站点 robots.txt 之前（[说明](https://developers.cloudflare.com/bots/additional-configurations/managed-robots-txt/)）。上线后执行 `curl -s https://<正式域名>/robots.txt`，确认 Cloudflare 托管段没有 disallow 搜索或 agent 类爬虫（OAI-SearchBot、ChatGPT-User、Claude-SearchBot、Claude-User、PerplexityBot 等）；训练类爬虫（GPTBot、ClaudeBot 等）是否 `Disallow` 由 owner 明确决定。
  - Free 计划关闭 Bot Fight Mode；Pro 及以上把 Super Bot Fight Mode 的 Verified bots 设为 Allow。Security Level 不设为 Under Attack，并在 Security → Events 留意 Browser Integrity Check 拦截 AI 爬虫的记录。
  - 可选只读核对：用有 Bot Management Read 权限的令牌请求 `GET /zones/{zone_id}/bot_management`（[API](https://developers.cloudflare.com/api/resources/bot_management/methods/get/)），期望 `ai_search`、`ai_user` 为 `disabled`，`ai_training` 为 `disabled` 或 `disallow`，`ai_bots_protection` 为 `disabled`。
  - 上线 1–2 周后，在 AI Crawl Control → Metrics 确认 OAI-SearchBot、ChatGPT-User、Claude-SearchBot、Claude-User 和 PerplexityBot 得到 2xx 响应。

  模板 `robots.ts` 在生产环境允许所有爬虫，`/llms.txt` 按 sitemap 的索引规则列出各语言可索引页面，二者都无需另行配置。
- [ ] 确认 Cloudflare 账户的 Workers observability 计费：`wrangler.jsonc` 默认全量开启 Logs 和 Traces，Cloudflare 自 2026-12-01 起对两者按 GB 计费。
- [ ] Owner 确认联系信息、法务文本、品牌内容和最终上线。
- [ ] 按语言/地区分别记录上线前 SEO 假设，并在 30/60/90 天复核各语言的搜索入口、询盘来源、询盘质量和内容缺口；没有真实买家信号的语言应停止扩展，而不是默认继续翻译。
- [ ] 按实际协作需要配置 main branch protection；未配置时只能记录“未强制”。

收件责任、服务配置、真实交付、域名和 Owner 确认，以及各层工程证明全部满足后，才能称为正式上线。SEO 复核属于上线后的经营安排；分支保护按实际协作需要配置。缺少任何必需证据时，只能记录“部分证明”或“未证实”。模板仓库验收只检查这些入口和交接要求，不自动部署或发送真实询盘。
