# 派生项目交接

这是派生站的交接、验证和正式上线清单。模板默认包含基础产品目录和产品详情页；派生站可以保留、扩展，或在完成依赖清理和门禁验证后移除。任何一层通过都不能自动替代下一层。

## 派生边界

- 会跟随：Git 中已跟踪的代码、测试、docs、`AGENTS.md` / `CLAUDE.md`、`.claude/rules/**`、workflows 和示例配置。
- 不会跟随：真实密钥、provider 资源、部署记录、DNS、GitHub ruleset 和 branch protection。
- AI 的通用工作方法使用全局 skills；项目事实遵循 `.claude/rules/content.md` 的编写入口，docs 解释使用与交接，rules 约束改动，不在多处独立维护同一个值或状态。
- 本清单在每个派生项目中重新开始，不继承模板或另一站点的绿灯。

## 第一轮替换

- 仓库和所有权：remote、默认分支、workflow 权限、Cloudflare 项目和负责人。
- 业务真相：`src/config/single-site*.ts`、`src/config/public-trust.ts`、`src/content/pages/**`、`messages/**` 和派生项目新增的真实 offering 页面。每个 offering 默认补齐应用场景、规格、材料、配置方式、交付边界和可验证证据；示例填写说明不能作为上线内容。
- 多语言交接：明确默认语言、目标语言/地区、URL 方案和每种语言的内容 owner；非默认语言必须有独立 URL、完整正文、页面级 SEO、`hreflang`/canonical 对应关系和可复核的翻译来源。不能把机器翻译占位页、IP 自动跳转或同 URL 多语言内容当作已完成。
- 品牌和法务：域名、联系方式、logo / favicon / OG 资产、主题、Privacy、Terms 和对外声明。
- 询盘和部署：按 `.env.example` 重新配置 Turnstile、rate limit、Airtable、Resend 和 Cloudflare Secrets，不复制真实凭据。
- 文档和规则：只保留当前项目真实存在的路径、命令和运行链。

研究、SEO 和原型阶段应使用外部研究工作区；代码仓库只接收已批准的事实、page map、页面内容包、原型和未证明边界，不继承原始研究报告或其他站点的 provider 证据。

## 设计与内容前置交接

派生项目进入页面设计前，必须从 `docs/派生站工作流.md` 完成对应阶段，并交接以下最小研究包；研究结论是上线前假设，不等于真实订单或市场验证：

- 业务事实包：产品、供应能力、地区、语言、交付边界和不可公开信息；
- 买家任务地图：主要角色、采购问题、决策担忧、需要的证据和下一步动作；
- SEO 页面地图：搜索主题、搜索意图、目标页面、语言/地区 URL、页面必须回答的问题和主要 CTA；
- 内容事实矩阵：产品事实、应用、规格、材料、配置、交付和证据的来源、公开状态和审核状态；
- Claim / Evidence 账本：每个对外承诺的证据、允许表达、禁止表达和审核状态；
- 待验证假设：上线后要用搜索、询盘和销售反馈复核的判断。

交接给设计前还要有：

- 已批准的 SEO page map 和 canonical owner；
- 已批准的 locale map：默认语言、非默认语言 URL 前缀、页面级 canonical、`hreflang` 对应表和 `x-default` 兜底页；
- 每个页面的 content package（Title、Meta、H1、区块正文、CTA、内部链接和证据）；
- 线框 / 低保真 HTML 或等价的信息架构原型；新页面类型至少提供一个页面级原型，小型派生可提交结构差异检查；
- 仍未证明的业务、SEO、设计或运行时边界。

未完成上述交接时，只能做结构草案，不能把示例文案、研究推测或占位内容当作正式页面内容。

## 设计与内容继承边界

默认继承：页面阅读逻辑、七类采购信息、蓝色语义、排版层级、间距节奏、组件边界、询盘路径、无障碍、性能和审查方式。设计规则见 `docs/design/设计真相.md`，代码实现规则见 `.claude/rules/ui.md`。

必须替换：产品事实、应用场景、规格、材料、配置方式、交付边界、可验证证据、联系方式、法务、SEO 内容和地区语言。

页面结构和视觉是推荐默认，不是不可变契约。业务事实、品牌定位或用户反馈支持变更时，可以调整；必须保留内容真实性、安全、可访问性和询盘交付能力，并验证受影响行为。

## 验证分层

| 层级 | 证明什么 | 不证明什么 |
| --- | --- | --- |
| 本地检查 | 改动相关的类型、lint、测试和必要构建 | 不证明部署或真实 provider |
| PR CI | GitHub runner 上的完整工程检查 | 不证明正式域名或 owner 收件 |
| `pnpm release:verify` | 当前 SHA 的本地 release 技术序列 | 不部署，不证明正式上线 |
| deployed smoke | 本次 Worker URL 的核心 GET 路由 | 不证明 DNS、TLS、Airtable 或 Resend |
| 真实业务验证 | Airtable canary、Resend 状态和 owner inbox receipt | 三份证据不能互相替代 |

多语言派生还要逐语言核对：公开 URL、`<html lang>`、正文语言、页面标题/H1、自指向 canonical、双向 `hreflang`、sitemap alternate、语言切换链接和非法 locale 的 404。搜索平台验证（Google Search Console、Bing Webmaster、Naver Search Advisor 等）属于外部平台证据，不由本地 build 或 `release:verify` 代替。

Next build、Cloudflare/OpenNext build 和 Playwright webServer 共用 `.next`，必须串行。真实 Airtable canary 使用：

```bash
PLAYWRIGHT_BASE_URL="$DEPLOYED_BASE_URL" pnpm canary:airtable
```

## Owner 与上线清单

- [ ] 指定 Airtable 备份收件箱的复核负责人和周期；按引用号核对未处理询盘，不能只检查带邮件失败标记的记录。
- [ ] 配置真实 Airtable base、table 和 PAT。
- [ ] 配置真实 Resend API key、发件域名和 owner 收件邮箱。
- [ ] 真实部署后运行 Airtable canary，并核对 API 响应与 Airtable 记录使用同一 `referenceId`。
- [ ] 单独确认 Resend provider 状态和 owner 收件箱实际收件。
- [ ] 人工确认正式域名、DNS、TLS 和 Cloudflare custom domain。
- [ ] Owner 确认联系信息、法务文本、品牌内容和最终上线。
- [ ] 按语言/地区分别记录上线前 SEO 假设，并在 30/60/90 天复核各语言的搜索入口、询盘来源、询盘质量和内容缺口；没有真实买家信号的语言应停止扩展，而不是默认继续翻译。
- [ ] 按实际协作需要配置 main branch protection；未配置时只能记录“未强制”。

收件责任、服务配置、真实交付、域名和 Owner 确认，以及各层工程证明全部满足后，才能称为正式上线。SEO 复核属于上线后的经营安排；分支保护按实际协作需要配置。缺少任何必需证据时，只能记录“部分证明”或“未证实”。模板仓库验收只检查这些入口和交接要求，不自动部署或发送真实询盘。
