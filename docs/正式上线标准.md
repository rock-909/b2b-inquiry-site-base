# 正式上线标准

这是公开上线的唯一判决正本。任何一层通过都不能自动替代下一层。派生站的替换、配置和 Owner 交接先按 `docs/派生项目交接.md` 执行。

| 层级 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| 本地开发 | 改动相关的类型、lint、测试和必要构建 | 不重复承担完整 CI、部署或真实 provider 证明 |
| PR CI | 完整测试、Chromium、Next/OpenNext 构建和安全扫描 | 不证明正式域名、真实 provider 或 owner 收件 |
| `pnpm release:verify` | 当前 SHA 的串行 release 技术序列 | 不部署，也不证明正式上线 |
| 部署 workflow | 真实部署及本次 `workers.dev` URL 的核心路由 smoke | 不证明正式域名、DNS、TLS 或 custom domain |
| 上线负责人 | 正式域名、DNS、TLS、联系信息、法务、provider 记录和最终批准 | 不用本地或 CI 绿灯代替人工确认 |

## 1. 本地工程证明

按改动范围运行 type-check、lint、相关 Vitest、内容检查和必要构建；涉及页面或浏览器行为时再运行对应 Playwright。普通 Next build、Playwright webServer 和 Cloudflare/OpenNext build 共用 `.next`，必须串行。

## 2. PR CI 与合并门禁

PR CI 证明声明的检查在 GitHub runner 上执行且通过。还要确认失败传播；如果项目声称 required status checks 或 branch protection 已强制，必须查证外部设置，否则只能记录“未强制”。

## 3. Release proof

`pnpm release:verify` 证明当前 checkout 满足 release manifest 的技术序列，包括内容、类型、测试、构建、Cloudflare 生成物、静态资源 header 和 Wrangler dry-run。

release proof 不是 public launch proof。固定 SHA、测试总数、warning 数量和一次绿灯不能成为永久标准。

## 4. 部署验证

部署 workflow 从本次 Cloudflare 部署输出提取 `workers.dev` URL，并运行 deployed smoke，确认首页、产品目录、一个真实 offering、未知 offering 404、联系/询价页、健康接口和安全文本。

这只证明本次 Worker URL 的核心 GET 路由。正式域名、DNS、TLS、custom domain route 和跳转由上线负责人人工确认，不能由 `workers.dev` smoke 代替。

workflow_dispatch 的 preview 分支只做“传入外部 URL 能否打开”的 surface smoke；它不构建、不部署，也不证明该 URL 对应当前 SHA 或当前构建产物。

## 5. 真实业务验证

显式运行 `PLAYWRIGHT_BASE_URL="$DEPLOYED_BASE_URL" pnpm canary:airtable`，确认真实 Turnstile 表单提交能写入 Airtable，并完成测试记录清理。缺部署地址或 Airtable 凭据时该命令必须失败。

Airtable canary、Resend provider 状态和 owner inbox receipt 是三份独立证据，不能互相代替。

## 正式通过条件

以下全部满足才可称为正式上线：

- 本地工程证明通过；
- PR CI 检查通过；如果项目要求 required checks 或 branch protection，外部强制力已确认；
- Cloudflare 构建、部署和本次 Worker URL smoke 通过；
- Airtable write canary 通过；
- Resend 状态和 owner inbox receipt 已单独确认；
- owner 确认正式域名、DNS、TLS、联系信息、法务、品牌内容和最终上线。

缺少任何一层，只能报告“部分证明”或“未证实”，不能报告“已正式上线”。
