# 质量门禁

本文记录当前仓库实际执行的本地、CI 和发布检查。配置文件和脚本是执行真相；本文用于解释触发时机、失败含义和证明边界。

## 触发矩阵

| 位置 | 触发方式 | 当前检查 | 失败后入口 | 证明边界 |
| --- | --- | --- | --- | --- |
| `pre-commit` | `git commit` 自动触发 | 暂存文件 Prettier、暂存 JS/TS ESLint、涉及 i18n 时的翻译同步 | 按 hook 输出修复对应暂存文件 | 只证明本次暂存内容，不证明全仓或构建 |
| `commit-msg` | `git commit` 自动触发 | commitlint | 修改提交信息 | 只证明提交信息格式 |
| `pre-push` | `git push` 自动触发 | 禁止直接推送 `origin/main`、生产和测试 TypeScript、Vitest、生产配置、Next build、client boundary artifact | 修复失败命令；feature branch 经 CI 合并 | 本地快速失败，不替代远端 CI |
| `pnpm website:check` | 开发者手动运行 | TypeScript、ESLint、Prettier、Vitest、Next build | 运行失败子命令 | 本地全仓工程检查，不含 OpenNext 和真实 Worker runtime |
| PR CI | PR 指向 `main` 或 `pr/**` 自动触发 | L1/L2 静态与架构、L3 Vitest/Playwright、Semgrep、L4 Next/OpenNext 构建和 artifact 合同 | 打开失败 job，运行同名本地命令 | GitHub runner 上的权威合并门禁；PR 不执行 Wrangler gzip dry-run |
| `main` CI | push 到 `main` 自动触发 | 同 PR CI，另执行 Wrangler preview dry-run | 打开失败 job；必要时本地运行 `release:verify` | exact `main` SHA 的构建证明，不等于部署成功 |
| `workflow_dispatch` CI | 手动触发 | 同 `main` CI | 同上 | 可为 exact SHA 补 Wrangler gzip 和构建证明 |
| `pnpm release:verify` | 本地手动；production 部署 workflow 自动调用 | 配置、类型、lint、format、Vitest、Chromium、Next/OpenNext build、artifact、headers、Wrangler dry-run | 修复首个失败步骤后从头重跑 | release lane 证明；不部署，也不证明真实 provider 或正式域名 |
| Cloudflare 部署 workflow | 手动选择 preview/production | preview 外部 URL smoke；production 严格配置、release verify、部署、部署后 smoke | 按 workflow 失败步骤处理 | 只证明本次 workflow 的部署和 smoke 范围 |
| weekly browser matrix | 每周及手动 | 全浏览器矩阵、零重试 | 根据 Playwright artifact 修复 | 暴露低频浏览器失败，不是每个 PR 的重复 gate |
| weekly dependency audit | 每周及手动 | production 依赖 audit，失败时创建 issue | 升级或评估受影响依赖 | 依赖漏洞信号，不证明应用不可利用性 |

普通 feature branch 的单独 push 不触发 `ci.yml`；创建指向受支持目标分支的 PR 后才进入 PR CI。

## 五层证明

| 层级 | 自动入口 | 主要对象 |
| --- | --- | --- |
| L1 Static | pre-commit、CI quality、release verify | TypeScript、ESLint、Prettier |
| L2 Architecture | CI quality、Semgrep、Cloudflare config checks | import、配置、安全和平台静态合同 |
| L3 Behavioral | Vitest、Playwright、weekly browser matrix | 单元、集成和浏览器行为 |
| L4 Build | Next build、OpenNext build、artifact/client-boundary checks | 构建产物、预渲染、包体和平台配置 |
| L5 Runtime | local/deployed smoke、production workflow、provider canary | Worker HTTP、已部署表面和明确执行的外部写入 |

## Next.js 官方实践适配

| 实践 | 判断 | 当前做法 |
| --- | --- | --- |
| TypeScript、ESLint、Prettier、tests、build | `ADOPT` | 本地综合检查和 CI 均覆盖 |
| staged file 格式和 lint | `ADAPT` | 使用 Lefthook check-only，不自动改写未暂存内容，不新增 `lint-staged` |
| 专用静态/架构规则 | `ADAPT` | 只保留本项目有真实 failure mode 的 dependency-cruiser、Semgrep 和 architecture tests |
| monorepo Turbo、Jest、Rspack、Rust/SWC fixture | `NOT_APPLICABLE` | 本项目没有消费者，不引入 |
| canary-only Cache Components / Partial Prefetching gate | `DEFER` | 等 OpenNext stable 兼容后独立验证 |

## 重复检查的处理

同一命令在本地和 CI 重跑属于不同环境的执行重复：本地用于尽早失败，CI 用干净 runner 提供权威证明。不要为了消除命令重复而删除关键 proof。

也不要把所有检查塞进每一层：

- pre-commit 只处理暂存文件，不运行测试或构建；
- pre-push 保留类型、测试和 Next build，不增加 OpenNext、Playwright 或 runtime smoke；
- CI 负责全仓、浏览器和 Cloudflare/OpenNext 构建；
- release verify 和部署 workflow 才处理发布前组合证明。

## 证明边界

- build 成功不等于 Worker runtime 正确；
- HTTP 200 不等于 Cache、PPR、prefetch 或 revalidation 正确；
- Wrangler dry-run 不等于已部署；
- Preview 可访问不等于当前 SHA 已部署；
- R2 binding 和 artifact 正确不等于真实写入成功；
- Airtable canary 不证明 Resend 投递和 owner 收件；
- 本地 `origin/main` guard 可被 `--no-verify` 绕过，不能替代 GitHub branch protection。

首次在新 worktree 使用本地 hook 时运行 `pnpm hooks:install`。不要提交 `.git/hooks` 生成文件或机器绝对路径。
