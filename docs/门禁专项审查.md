## 结论

当前问题不是缺少检查工具，而是合并阻断没有落地、部分检查的成功语义不可靠，以及不同证明层被混用。不要再加一套总控框架；先让已有检查承担明确责任。

### 1. P1：远端 main 没有强制保护

GitHub `GET /repos/rock-909/b2b-inquiry-site-base/branches/main` 实际返回 `protected: false`。rulesets 和 branch protection API 均返回 403，明确提示升级 GitHub Pro 或公开仓库才可用；不是根据缺少仓库配置猜测。

因此 `CI 汇总` 是检查结果，不是当前实际生效的强制合并条件。本地 `origin/main` guard 可被跳过、换 remote 名称绕过，不能替代它。

建议：由负责人决定是否启用支持私有仓库保护的方案，然后要求同一提交的 `CI 汇总` 成功、限制直推与绕过。不要为了门禁直接公开仓库。在此之前保留本地重检查作为提前发现问题的措施，但不能宣称它提供远端保证。

### 2. P1：React Doctor 分析不完整仍返回成功

位置：`package.json:20`、`.github/workflows/ci.yml:47`。

本地真实执行 0.9.13 的 JSON 扫描得到：退出码 0，error/warning 均为 0，但 `projects[0].complete: false`，原因是读取已删除、尚未暂存的 `cloudflare-config-open-next-hook.mjs` 发生 ENOENT。现有 contract 测试只检查命令包含 `--blocking warning`，不能证明该失败会阻断。

需求整改的代码质量另用临时独立 Git 索引完成了完整扫描，没有改动用户暂存区；这只是本次验证办法，不是门禁修复。尚未证明干净 CI checkout 也会触发同一个删除场景。

建议：优先采用已验证修复此行为的上游版本；否则在现有入口检查 JSON 完整性及退出码，未知/不完整结果失败。只需一个最小入口及不完整报告回归测试，不应维护 vendor 私有补丁。

### 3. P1：production 的授权与质量前提没有闭合

位置：`.github/workflows/cloudflare-deploy.yml:76`、`:173`。

- 分支限制只比较 `GITHUB_REF_NAME == main`，没有确认 `GITHUB_REF == refs/heads/main`，同名 tag 在条件逻辑上也会通过；没有创建 tag 或实际触发部署验证。
- job 未绑定 GitHub environment；API 返回 environments 数量为 0，没有 environment 审批边界。
- production 调用 `release:verify`，但它不包含 Semgrep、React Doctor、knip、独立 client-boundary 检查，也不查询该 SHA 的 CI 成功结果。配合未保护的 main，不能把它视作“合并检查已通过后才发布”。

建议：校验完整 branch ref，并验证同一 SHA 的 CI 成功。单人模板不强行增加多人审批；是否需要 production environment 审批由真实发布责任决定。远端策略未经授权不改。

### 4. P2：PR 的 Wrangler 打包证明只是人工约定

位置：`.github/workflows/ci.yml:246-269`。

PR 明确跳过 dry-run，却可以得到成功的 Cloudflare job 和 CI 汇总。summary 要求人工补 exact SHA 的手动运行，但不存在对该补充证明的自动检查。

本次本地 dry-run 不需要生产发布 token 即可成功。建议验证无凭据 PR runner 后直接让 PR 执行 dry-run，删除人工补运行约定，而不是新增审批脚本。保持“不上传、不部署”的边界。

### 5. P2：production release 使用 preview 打包演练，凭据检查也不证明 Worker 配置

位置：`scripts/quality/checks/release-verify.js:53-55`、`.github/workflows/cloudflare-deploy.yml:131-166`。

production 调用的 release 末尾仍固定 `--env preview`。它证明 preview 打包拓扑，不证明 production 的对应打包参数。严格配置步骤检查 GitHub secrets，部署步骤没有同步或核验 Worker secret 配置；两处配置不能直接视作同一个事实。

建议：发布演练使用实际目标环境；明确 GitHub 构建输入与 Worker 运行配置的责任。保留真实 provider 验收作为人工上线条件，不用健康检查代替。不要为此自动发送真实询盘或同步 secrets。

### 6. P2：周检矩阵没有按设备能力分配用例

位置：`playwright.config.ts:60-76`、`tests/e2e/internationalization.spec.ts:119`、`tests/e2e/navigation.spec.ts:77`。

远端 2026-09-07 周检 run `34138778350`：349 passed、4 failed、2 did not run。失败包括移动设备执行桌面语言按钮流程、Mobile WebKit 不支持 mouse.wheel，以及 Firefox 遮罩点击后菜单未关闭。前两项已由日志和当前用例前提对应确认；Firefox 需浏览器复现才能区分产品缺陷与输入模拟问题。

建议：桌面用例显式声明桌面视口，触屏行为使用受支持的触摸输入，保留真正有不同风险的设备覆盖。无共享状态的语言旅程不必 serial，以免一个失败使后续测试不运行。不要通过增加重试、整组 skip 或删除移动端证明掩盖问题。

本次新增 pending 测试已显式设置桌面视口，避免把第一阶段的新测试带入同类错误；上述历史矩阵问题没有自动修复。Chromium 成功不代表整个矩阵成功。

### 7. P2：部分超时边界与实际工作不匹配

位置：`scripts/quality/checks/release-verify.js:84-92`、`playwright.config.ts` 的 webServer、`.github/workflows/cloudflare-deploy.yml:307-309`。

- 本地 release 子进程没有 timeout；CI 只有整个 job 的总预算。
- release 强制重建 Playwright 服务，但 CI webServer 仍只有 60 秒，注释却假设已经构建。慢 runner 上可能在正式测试前误失败。
- 部署前等待的 curl 没有单次连接/总时限；30 次循环不能保证计划内返回，最终只能依靠 job 超时。

建议：先给这些实际存在的等待设定清晰上限；构建和仅启动使用不同预算。production 15 分钟总预算是否不足还需真实运行时长，不凭感觉上调。

### 8. P2：本地 hook 实际入口与仓库说明不一致

现场 `core.hooksPath` 未配置，实际 `.git/hooks` 中有 Lefthook 生成脚本，当前 hook 并未消失。但没有采用仓库 `.githooks` 的入口；生成脚本包含本机路径，找不到 Lefthook 的最终分支仅 echo，可能成功退出。仓库 wrapper 则明确 exit 1。

此外 `scripts/git/lefthook-hook.sh:7-12` 使用 `LETHOOK`/`LETHOOK_BIN`，而生成脚本使用 `LEFTHOOK`/`LEFTHOOK_BIN`，两个入口的变量契约不同。

建议：统一到已有 `hooks:install` 入口，并修正变量名称，不保留第二种私有环境变量约定。本次没有修改 Git config 或用户 hooks。暂存文件清单不自动等于暂存字节快照；未做 partial-stage 隔离实验，不把当前 pre-commit 宣称为提交内容的完整证明。

## 取舍：哪些保留，哪些可以少做

| 层 | 应负责的最小内容 | 判断 |
| --- | --- | --- |
| pre-commit | 本次文件格式/lint，相关翻译检查 | 保留；不要加 build |
| commit-msg | 约定式提交格式 | 无外部消费者证据，低优先级可取消强制；不是安全门禁 |
| pre-push | 尽早发现错误，不负责发布真实性 | 当前暂留；远端强制落地后移走全量测试/build，按需手动运行 |
| PR CI | 干净环境的静态、行为、平台构建与打包证明 | 保留，并解决完整性和 dry-run 缺口 |
| CI 汇总 | 所需 jobs 全部 success | 现有 always + 显式非 success 失败逻辑正确，保留 |
| release | 目标环境配置、构建/产物、发布后 HTTP | 同 SHA 的 CI 可复用时移走重复 lint/test；先不要新增跨 workflow 缓存或产物复用系统 |
| weekly browser | 独有浏览器/触摸风险，零重试 | 保留并修正能力映射；不必每种设备重复所有无关组合 |
| weekly audit | 漏洞发现与负责人跟进 | 保留；continue-on-error 后显式 exit 1 已正确阻断该 workflow |
| Lighthouse | 性能相关改动时测量 | 按需保留，不变成每次推送必跑 |
| provider/正式域名验收 | 真实交付、收件、DNS/TLS、所有者确认 | 保留独立验收，不伪装成 CI 自动证明 |

当前 CI quality 是其余 jobs 的共同前置，能省掉明显失败后的昂贵工作；各 job 独立安装是 runner 隔离，不应仅因文本重复合并。Next 分析构建与 OpenNext 最终构建有不同产物用途，不是可以直接删掉的同一证明。

## 权限、重试、历史运行的核对

- GitHub 默认 workflow 权限实际为 read，不能把 CI 没写 permissions 直接报成当前写权限漏洞。建议显式 `contents: read`，避免继承值未来漂移；weekly audit 的 issues: write 有真实消费者。
- production 不取消进行中的同组部署，preview/CI 允许取消旧运行，现有取舍合理。
- CI 浏览器最多重试两次，weekly 为零重试；前者不证明首次通过。保留失败 artifact，不把首次失败隐藏到只剩绿色总数。
- 生产部署凭据在 shell 里直接插值，宜改用 env 引用，避免值被当作 shell 内容解释；当前没有不可信人员控制 secret 的证据，不夸大成已发生利用。
- smoke 共用 fetch 使用 AbortSignal.timeout，覆盖响应体读取；不需要再造 HTTP 检查框架。
- CI run `34101624885` 在 HEAD 上成功，但同 SHA 的 weekly browser 与 dependency audit 均失败。这不是 CI 汇总漏统计自己的 needs，而是周期任务根本不在其证明范围。
- dependency audit run `34135418509` 是 Browserslist 两项 high 告警：GHSA-c83g-rgw3-j3cx、GHSA-73wf-gq98-2v4g，不是网络失败。这里只确认该时点告警和失败传递，未据此断言线上可利用，也未擅自升级依赖。
