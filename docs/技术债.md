## F01 — OpenNext config gate：四层间接保护一个 12 行文件

**位置**：`scripts/quality/checks/cloudflare-config-check.js`、`cloudflare-config-open-next-hook.mjs`、`cloudflare-config-open-next-runner.mjs`

### 背景

第一轮审查第 6 项发现 config gate 原本用 AST 解析 `open-next.config.ts` 的 token 来“猜”配置结构；第一轮整改（PR #33）升级为“运行时方案”:真的去 import 配置。由于 `open-next.config.ts` 里 `import { defineCloudflareConfig } from "@opennextjs/cloudflare"` 无法在测试环境真实加载(TS + 包副作用),整改者造了一个自定义 ESM loader 拦截该 import 并注入伪造实现,用 globalThis sentinel 记录调用、伪造返回 shape。

### 为什么它是债

1. **语义漂移**：gate 证明的是自定义 mock 包的行为，不是真实 `@opennextjs/cloudflare` 会怎么理解这份配置。上游包若改变量签名或返回 shape，gate 无法发现。
2. **四层机制**：custom ESM loader + globalThis sentinel + subprocess runner + 残留 AST token scan，共同保护一个 12 行文件。间接链越长，任一层改坏都会导致误报（CI 假红）或漏报（配置破坏悄悄上线）。
3. **维护入口多**：新增 fixture 或 topology 时需先检查 loader 拦截逻辑是否覆盖，而非只写配置和断言。

### 为什么留存

重构为"真实加载 + 极窄 exact-shape contract"会重写发布 gate（安全性边界），回归风险换取代码可读性；现状稳定工作、有完整测试覆盖（`cloudflare-config-check.test.ts` 绿）。风险等级是维护性而非正确性，不紧急。

### 触发重估条件

- `@opennextjs/cloudflare` 升级后 gate 误报/漏报
- 新增 fixture 时发现 loader 覆盖不住
- 发布链路本身需要改动，顺手一起做

## F05 — Route test lane：五份 mock 注册壳（约 163 行）

**位置**：`src/app/api/inquiry/__tests__/route-harness.ts` + 5 个 lane 文件（request-admission / rate-limiting / payload-validation / turnstile-gate / lead-delivery）

### 背景

第一轮整改（PR #31）把 39 个 route 测试拆成 5 个 lane，共享 `route-harness.ts`。harness 收口了 mock **函数**（`routeMocks` 里的 `vi.fn()`），但每个 lane 文件仍各自复制 7 条 `vi.mock(...)` 注册（约 27 行 × 5 份）。

### 为什么它是债

1. **维护点 ×5**：新增 route boundary 或改 mock 的 module path 时，5 个文件需同步改，漏一个就是静默行为差异。
2. **一致性靠人工核对**：某个 lane 忘了补新 mock，该 lane 会悄悄用真模块，极难发现。
3. **约 163 行重复样板**：文件变长、diff 噪音大，掩盖行为断言。

### 为什么留存（NO-GO 论证）

- `vi.mock()` 是 vitest 静态提升机制：必须在文件顶层声明、按文件作用域生效，不能安全移入普通 helper。
- 集中到全局 setup 会让 mock 全局生效、跨 lane 串扰 —— 破坏 lane 隔离（拆 lane 的核心价值）。
- 收益/风险不对称：约 163 行样板 vs 引入 hoisting 魔法 + 破坏隔离。`routeMocks` 已收口可变状态，重复的只是静态注册声明，行为正确性有测试保证。

### 触发重估条件

- 新增第 6 个 lane 时重新掂量
- vitest 大版本引入更干净的共享 mock 原语
- 有人改 mock path 时实际踩坑漏改

## F06 — 负向契约：保护"某东西不存在"

**位置**：`/security-policy.txt` 404 实现、已删除 blog 的断言、退休 surface 的 no-store 断言等

用运行时代码和测试保护"某东西不存在"（已退休 surface 继续返回 404、已删功能无残留引用）。这被判定为**防回归的有意设计**而非债务：删除这些保护会让退休 surface 悄悄复活而不被发现。维持现状。

**触发移除条件**：对应 surface 真正重新上线时，删除保护并恢复正向契约。

## F04-impl — `sharedToolingRules` 共享语义的隐性成本

R2-F04 整改（PR #40）把 `config-and-dev-tools` 与 `scripts` 两个 block 的 22 条逐字相同规则抽为共享常量。代价：未来修改一条共享规则会**同时影响两个 scope**。这是共享语义的预期代价（常量上方注释已写明）。经 `eslint --print-config` 全 23 文件矩阵对账证明零行为变化。

**触发拆分条件**：两 scope 对某条共享规则的需求开始分叉（一个要 warn 一个要 off），此时把该规则从共享常量移回各自 block。
