# 派生站设计工作流

这套流程用于当前站和所有工业 B2B 派生站。默认继承同一套设计内核、色彩语义和询盘逻辑；只有业务事实确实不同，才改变页面结构或视觉表达。

## 总流程

`Context -> Shape -> Reference -> System -> Plan -> Implement -> Review -> Harden -> Derive`

### 1. Context：先回答业务问题

- 谁访问：采购、工程、技术、质量、安装或老板？
- 他在判断什么：是否适用、规格是否匹配、供应是否可靠、交付是否可控？
- 站点目标是什么：让合适的人提交可处理的询盘，而不是只获得浏览量。
- 哪些事实可以公开：产品、应用、规格、材料、配置、交付、证据和边界。

### 2. Shape：把回答变成页面结构

页面默认按这条顺序组织：

1. 先说明产品或业务是什么；
2. 再说明适用场景和采购角色；
3. 再给出规格、材料和配置方式；
4. 再说明交付边界与可验证证据；
5. 最后提供明确的询盘入口。

产品详情页默认保留七类采购信息：产品事实、应用场景、规格、材料、配置方式、交付边界、可验证证据。产品列表页负责筛选和进入详情页，联系页负责补齐跨产品或项目级需求。

### 3. Reference：研究最大公约数

参考 Vercel、Cursor、Apple、IBM、Linear、OpenAI 等网站时，不复制行业外观，而是提取可迁移的共同原则：

- 内容先于装饰；
- 清晰的标题和单一主行动；
- 统一网格、留白和对齐边缘；
- 状态有反馈，但动效克制；
- 复杂内容逐步展开，不把关键信息藏在交互之后；
- 颜色承担语义，不承担无意义的换肤。

每条参考必须回答：它如何安排内容、控制比例、使用颜色、制造节奏、删掉什么，以及为什么适合当前买家。

### 4. System：先用现有系统

- 整体色彩入口是 `src/app/theme.css`；
- 组件结构和样式入口是 `src/components/ui/*`；
- 产品事实入口是 `src/config/offerings.ts`；
- 共用文案入口是 `messages/base/{locale}/messages.json`；
- 页面内容入口是 `src/content/pages/{locale}/*.ts`。

默认色彩语义：浅色或中性背景，蓝色同时承担主要行动、技术可信和信息强调；绿色、黄色、红色只用于状态。派生站默认继承这套色彩系统，不为了制造差异而换肤。

### 5. Plan：先列区块，再列实现

每个页面先写一张简表：

| 区块 | 买家问题 | 内容来源 | 主行动 | 证据要求 |
| --- | --- | --- | --- | --- |
| 首屏 | 这是什么？ | 产品事实 | 查看详情/询盘 | 不做未经确认的承诺 |
| 应用 | 适合我的场景吗？ | 应用场景 | 继续判断 | 明确适用边界 |
| 规格 | 能否匹配参数？ | 规格 | 配置或询盘 | 单位、范围、限制 |
| 材料/配置 | 如何选？ | 材料、配置 | 获取建议 | 区分标准和定制 |
| 交付/证据 | 能否放心采购？ | 交付、证据 | 提交询盘 | 记录、图纸、证书或报告 |

### 6. Implement：自下而上落地

1. 先复用现有布局、按钮、卡片和表单；
2. 再用语义 token 控制颜色、间距、边框、圆角和状态；
3. 用原生 HTML 表达列表、表格、链接和表单；
4. 动效只服务状态反馈、连续关系和注意力引导，优先 CSS，并支持 `prefers-reduced-motion`；
5. 关键信息必须在无 JavaScript 时仍然可读。

### 7. Review：按设计品味审查

逐页检查：

- 首屏是否一眼看懂；
- 信息是否按采购决策顺序出现；
- 标题、正文、规格和 CTA 是否有明显层级；
- 留白是否在分组，而不是制造空洞；
- 颜色是否只强调真正重要的内容；
- 是否存在多余卡片、装饰、阴影、动画或文案；
- 320px/375px、200% 缩放、键盘、读屏和 reduced-motion 是否成立。

### 8. Harden：用真实证据收口

最窄验证顺序：内容检查、相关测试、类型、Lint、React Doctor、生产构建、真实浏览器桌面/移动检查，再做可访问性检查。Local green 不等于正式部署或真实 provider 成功。

### 9. Derive：复制系统，不复制假内容

派生站复制的是页面模式、色彩语义、间距节奏、组件边界和审查方法；必须替换为真实的产品事实、应用场景、规格、材料、配置方式、交付边界和可验证证据。示例填写说明不能直接上线。

## 停止条件

需求对应的页面、内容和验证已经完成后立即停止。不因为“以后可能会有第二个调用方”增加抽象、依赖、配置或新的设计层。
