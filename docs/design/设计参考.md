# 设计参考

本文记录已经判断值得借鉴的设计细节、原则和使用边界，服务当前站及工业 B2B 派生站。

本文不是品牌规范，也不是组件库。权威关系如下：

- `docs/design/设计真相.md`：当前项目必须遵守的设计规则；
- `docs/派生站工作流.md`：如何研究、决策、实现和验收；
- 本文：外部参考中值得保留的设计证据和可迁移原则。

外部网站只提供证据和启发，不直接决定业务内容、SEO、页面结构或品牌视觉。任何参考进入实现前，都要回到买家任务、产品事实和现有 Token 验证。

## 使用方法

每次引入一个参考时，先回答：

```text
它解决了哪个用户问题？
它体现了什么设计原则？
能否落到现有页面、Token 或组件？
是否会增加没有业务收益的复杂度？
如何验证它在本项目中有效？
```

满足以下任一条件，直接不采用：

- 无法映射到当前买家的真实任务；
- 只能复制外观，无法解释行为或内容价值；
- 无法落到现有页面、Token 或组件；
- 需要新增依赖、客户端边界或长期维护成本，但没有明确收益；
- 会隐藏产品事实、规格、交付边界或询盘入口。

## 参考分层

| 类型 | 主要回答 | 可以借鉴 | 不能证明 |
| --- | --- | --- | --- |
| 真实产品流程 | 用户如何完成任务 | 信息架构、步骤、反馈 | 工业采购一定采用同样流程 |
| 页面叙事 | 内容如何被组织和展开 | 标题、比例、节奏、CTA | 转化效果和业务真实性 |
| 设计模式 | 某个细节为什么有效 | 状态、错误、展开、反馈 | 适合所有业务场景 |
| 设计系统 | 规则如何保持一致 | Token、组件状态、命名 | 本项目应直接采用其视觉语言 |
| 交互指南 | 控件如何被理解和操作 | 可发现性、反馈、可恢复 | SEO、产品定位和内容策略 |
| 动效参考 | 状态如何连续变化 | 过渡、反馈、层级 | 动画数量越多越好 |
| 质量标准 | 如何验收 | 无障碍、性能、稳定性 | 设计品味和品牌判断 |

## 已确认的共同原则

### 1. 内容先于装饰

- 首屏先回答“这是什么、适合谁、下一步是什么”；
- 标题和核心结论先于图片、渐变和动效；
- 装饰不能替代产品事实、规格、证据或交付边界；
- 如果删除装饰后页面信息仍然成立，优先删除装饰。

**工业 B2B 用法**：先让采购人员完成产品判断，再用线条、图片和微动效建立识别度。

### 2. 一个区块解决一个主要问题

常见问题包括：

```text
这是什么？
适合我的场景吗？
规格能否匹配？
如何配置？
你能交付什么？
为什么相信你？
下一步如何询盘？
```

区块如果没有明确问题，不因为“页面看起来完整”而保留。

### 3. 视觉层级来自差异，不来自堆叠

- 用字号、字重、间距、位置和对比度建立层级；
- 一个页面只保留一个主要行动；
- 次要动作降低视觉权重，但不能降低可发现性；
- 不同时使用过大的字号、粗阴影、强渐变、厚边框和多种卡片来制造重点。

### 4. 留白用于分组和节奏

- 区块之间的间距应表达内容关系；
- 相关内容靠近，不相关内容拉开；
- 留白不能让首屏缺少产品事实或 CTA；
- 窄屏优先保留阅读顺序和触控空间，而不是机械缩小桌面布局。

### 5. 颜色承担语义

当前项目默认：

```text
浅色或中性背景
蓝色：主要行动、技术可信、信息强调
绿色/黄色/红色：成功、警告、错误等状态
```

- 蓝色不平均铺满页面；
- 状态不能只依赖颜色表达；
- 派生站默认继承这套颜色语义，不为制造差异而换肤；
- 颜色变化必须能解释为业务、可访问性或状态需要。

### 6. 先设计行为，再设计表面

组件实现顺序：

```text
语义结构
→ 默认行为
→ 键盘与焦点
→ 响应式边界
→ 状态反馈
→ 视觉 Token
→ 动效
```

外部组件只能作为原料。正式使用前，必须统一项目的 Token、内容结构、状态、响应式和无障碍行为。

## 重点参考一：Apple Human Interface Guidelines

来源：[Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/)

### 值得借鉴

- **可发现**：用户能看出什么可以操作，以及操作后会发生什么；
- **反馈**：筛选、提交、下载、切换和展开都要给出清晰结果；
- **可恢复**：错误提示说明问题、原因和修复方式；
- **连续性**：界面变化保持位置、层级和因果关系；
- **减少认知负担**：只在需要时展示复杂选项；
- **可访问**：键盘、焦点、文字大小、对比度和减少动态效果不能作为后补；
- **动效有目的**：解释状态、层级或导航，不延迟用户任务。

### 工业 B2B 转化

| HIG 原则 | 工业站用法 |
| --- | --- |
| Feedback | 询盘提交、筛选结果、下载和主题切换明确显示结果 |
| Discoverability | CTA、规格入口、图纸下载和可展开内容清楚可见 |
| Error recovery | 表单错误就地说明，保留用户已填写内容 |
| Progressive disclosure | 先显示核心规格，复杂定制条件按需展开 |
| Accessibility | 规格表、表单、状态和焦点在键盘和窄屏下成立 |
| Motion | 用短过渡表达变化，不用页面级 reveal 隐藏内容 |

### 不直接复制

- iOS 的导航、Tab Bar、手势和系统控件外观；
- Apple 的字体、圆角、玻璃效果和品牌黑白配色；
- 面向消费设备的交互假设；
- 任何会替代工业产品事实的情绪化表达。

## 重点参考二：Vercel、Cursor、OpenAI、Linear、IBM

这些网站不按业务行业复制，只作为跨产品的最大公约数参考。

### 值得借鉴的共同点

#### 克制

- 页面保留少量真正重要的视觉重点；
- 不用连续动画、装饰性渐变和多余卡片填满空间；
- 让高质量排版、对齐和留白承担主要视觉工作。

#### 强层级

- 首屏有明确主标题和核心结论；
- 主要行动与次要行动有清晰差异；
- 复杂信息按层级展开，不把所有内容挤在同一视觉平面。

#### 系统一致

- 颜色、间距、边框、圆角和控件状态有稳定规则；
- 相同语义的组件在不同页面保持相同行为；
- 页面差异来自内容和任务，而不是随意换主题。

#### 状态清晰

- 加载、成功、失败、空结果和禁用状态可理解；
- 用户始终知道系统正在做什么；
- 重要任务不依赖 hover、自动播放或动画完成。

### 工业 B2B 转化

```text
中性画布
→ 清晰产品结论
→ 少量蓝色强调
→ 规格和证据分层
→ 明确询盘动作
```

这些原则可以继承；具体品牌色、页面比例、动画形式和视觉素材不能直接复制。

## 重点参考三：Yan Liu Design

来源：[Yan Liu Design](https://yanliudesign.live/)

### 值得借鉴

- **编辑化布局**：页面像一篇有节奏的长篇内容，而不是由大量同质卡片堆成；
- **大标题锚点**：用少量超大标题建立区块识别，再用短说明解释上下文；
- **Sans + Mono 角色分工**：Sans 用于标题和正文，Mono 用于导航、分类、日期、阅读时长和技术元数据；
- **粗边框建立秩序**：用边界线、分栏线和留白表达区块关系，减少对阴影的依赖；
- **大比例图片与内容并置**：图片承担识别和吸引注意，文字承担项目说明和行动入口；
- **元数据提高可浏览性**：分类、日期、阅读时长和标签帮助用户快速判断内容；
- **图片状态轻量变化**：灰度图片在 hover 时恢复颜色并轻微放大，提供反馈而不抢夺内容；
- **栏目化内容资产**：作品、实验、文章、演讲和过程分别组织，形成持续更新的内容结构。

### 工业 B2B 转化

| Yan Liu Design | 工业 B2B 站 |
| --- | --- |
| Selected Works | Featured Products / Case Studies |
| Vibe Coding | Engineering Experiments / Technical Capabilities |
| Writings | Technical Resources |
| Speaking | Certifications / Industry Presence |
| About the Process | Manufacturing / Delivery Process |
| Mono 元数据 | 型号、规格、单位、版本、适用行业和更新时间 |

适合将这种编辑化节奏用于首页重点产品、案例、应用和技术资源；产品详情页仍然优先保证规格、交付边界、证据和询盘入口。

### 不直接复制

- 荧光绿品牌色；当前项目继续使用蓝色作为行动、技术可信和信息强调色；
- 个人名字式的超大 Hero；工业站首屏必须说明产品、应用或供应能力；
- 个人博客栏目和职业叙事；改为产品、应用、工程、资源、案例和交付内容；
- 极端留白和全屏作品集比例；留白必须服务采购判断；
- 仅依赖 hover 的图片变化；触屏和无 JavaScript 时内容仍需完整可读。

## 重点参考四：设计系统和组件资源

适用参考包括 Component Gallery、Design System Checklist、Base UI、React Aria、Radix、ReUI 等。

### 使用顺序

```text
先确认用户任务和组件行为
→ 横向比较成熟系统
→ 选择现有项目能承接的基础实现
→ 使用本项目 Token 和内容规范收敛
→ 检查状态、无障碍、响应式和性能
```

### 采用边界

- 行为复杂的控件优先使用项目已有的本地封装；
- 普通文本、列表、规格表、按钮和表单优先使用原生 HTML；
- 外部组件代码不能直接成为项目设计系统；
- 一个组件只有一个真实调用方时，不为“以后复用”增加抽象；
- 引入新依赖前必须指出真实消费者和可复现收益。

## 模块化组装原则：把参考转成可执行前端

AI 适合读取高质量参考、比较候选模块并完成项目内适配，不适合凭空决定页面结构或品牌风格。外部模块是原料，不是本项目的设计系统。

### 使用顺序

```text
定义买家任务
→ 选择模块类型
→ 比较 2～3 个参考
→ 提取行为和结构
→ 接入现有 Token 与组件
→ 组合页面
→ 做系统一致性和质量审查
```

### 适合模块化组装

```text
产品卡片、规格表、参数对照、应用场景、材料说明
配置选项、证据列表、询盘表单、筛选控件、状态反馈
主题切换、展开/收起、下载反馈和错误提示
```

### 不适合直接拼装

```text
首页 Hero、品牌核心叙事、产品定位、应用说明
交付边界、认证与证据表达、询盘字段和地区内容
```

这些内容必须由业务事实、买家任务和证据决定，不能从组件市场推导出来。

### 给 Agent 的输入约束

处理前端设计任务时，至少提供：

```text
页面任务和目标买家：
需要解决的具体 UI 问题：
当前项目的设计内核：
可以参考的模块：
必须继承的 Token、组件和行为：
不能复制的品牌外观：
必须通过的无障碍、响应式、性能和 no-JS 条件：
```

先让 Agent 比较参考并说明取舍，再实现。不要直接复制完整页面、完整组件库或未经筛选的代码。

### 视觉方案必须真正分化

生成多个候选时，不要只更换颜色、渐变或字体。候选方案至少应在以下两个维度上形成明确差异：

```text
内容密度
网格结构
图片的角色
证据的表达方式
排版比例
视觉节奏
```

先淘汰最接近默认模板的方案，再选择最符合买家任务、产品事实和当前设计内核的方向。禁止项只能减少明显错误，不能代替真正的设计取舍。

### 组装后的审查

- 颜色、字体、间距、圆角、边框和阴影是否来自同一套系统；
- 相同语义的组件在不同页面是否保持相同行为；
- 产品事实、规格、证据和询盘入口是否仍然优先；
- 默认、Focus、Loading、Error、Empty 等适用状态是否成立；
- 是否引入了不必要的依赖、客户端边界或动画；
- 320px/375px、键盘、reduced-motion 和无 JavaScript 是否成立。

如果每个模块单独看起来不错，但组合后像来自不同网站，应退回重新筛选或统一 Token，而不是继续叠加装饰。

### 双通道设计审查

设计结果不得只由生成它的同一个 Agent 自评。审查分成两个互不影响的通道：

```text
品味审查：层级、节奏、克制、模板感、买家理解成本
确定性审查：事实、对比度、键盘、状态、窄屏、no-JS、性能和浏览器行为
```

最后由主 Agent 综合两路结果，明确区分：

```text
必须修复
可以接受
不属于当前范围
```

确定性检查没有发现问题，不代表视觉方案有品味；品味审查认可，也不代表运行行为成立。

## AI 辅助视觉生产：规范、生成与 Figma

AI 视觉生成只能在页面内容包和低保真结构批准后使用。先把现有设计规范、Token、组件边界和禁止项作为生成约束，再生成视觉候选并转换到 Figma 继续调整。

```text
已批准内容和区块顺序
→ 提取设计规范与项目约束
→ 生成 2～3 个视觉候选
→ 转入 Figma 比较和调整
→ 回到真实仓库实现
→ 浏览器、无障碍和性能验收
```

### 适合解决

- 首屏比例、图片与文字关系；
- 规格、证据和 CTA 的视觉构图；
- 页面密度、留白和品牌氛围；
- 同一内容结构下的视觉方向比较。

### 不能替代

- 业务事实、SEO、买家任务和页面内容包；
- 表单、键盘、状态、响应式和无 JavaScript 行为；
- 生产组件、内容源、测试和部署合同。

AI 生成图用于探索，Figma 用于协作和视觉确认，生产代码与真实浏览器行为才是最终实现。生成结果不得直接覆盖仓库，也不能因为视觉稿存在而跳过低保真结构和运行时验证。

## 重点参考五：动效资源

适用参考包括 Transitions.dev、Motion Primitives、Animate UI，以及经过筛选的品牌动效案例。

### 采用顺序

```text
先确认状态变化
→ 选择最短、最轻的过渡
→ 优先 CSS 和现有浏览器能力
→ 支持 prefers-reduced-motion
→ 检查输入阻塞、布局稳定性和移动端性能
```

### 工业站优先级

1. 询盘提交成功、失败和进行中；
2. 产品筛选、展开和切换；
3. 主题切换和焦点反馈；
4. CTA hover / focus；
5. 低频品牌节点的轻量氛围动效。

不要为首屏、规格、证据或询盘入口增加必须等待的 reveal 动画。

## 设计审查速查表

### 内容与层级

- [ ] 首屏能说清产品是什么、适合谁和下一步是什么；
- [ ] 每个区块对应一个买家问题；
- [ ] 核心规格、交付边界和证据没有被装饰掩盖；
- [ ] 主要 CTA 只有一个，且动作含义明确。

### 交互与状态

- [ ] 用户知道哪些元素可以操作；
- [ ] 操作后有明确反馈；
- [ ] 错误可理解、可修复；
- [ ] 默认、Focus、Loading、Error、Empty 等适用状态已处理；
- [ ] 关闭动画后任务仍然成立。

### 视觉与工程

- [ ] 留白表达分组，而不是制造空洞；
- [ ] 蓝色只用于真正需要强调的内容；
- [ ] 没有为装饰新增不必要依赖或客户端边界；
- [ ] 320px/375px、键盘、200% 缩放和 reduced-motion 成立；
- [ ] 参考细节没有破坏无 JS 内容、询盘入口和页面性能。

## 维护规则

- 本文只保留已经能影响当前设计决策的参考；
- 新增参考必须说明适用任务和不照搬项；
- 参考如果连续两次不能改变页面、系统或审查决策，移出本文；
- 本文原则与 `设计真相.md` 冲突时，以 `设计真相.md` 和运行行为为准；
- 不以收藏数量、页面数量或组件数量衡量参考质量。
