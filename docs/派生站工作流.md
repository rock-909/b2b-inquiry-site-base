# 派生站工作流

本文概述从业务想法到可运行网站的工作，以及各环节可借鉴的方法。它延续项目讨论中的方法方向，不是行业统一流程，也不代表整套 Agent 方法已通过实际派生验证。方法按问题选用，已有事实、内容和设计可以复用；普通小修直接处理受影响部分，不重做建站流程。

## 总流程

**业务目标。** 先弄清网站帮助谁完成什么、企业希望获得什么结果。JTBD 从买家所处情境和希望取得的进展理解需求；任务分析进一步看他们如何判断、比较和联系。目标—信号—指标的思路帮助区分“想要更多询盘”和什么变化值得观察。已有可靠销售记录时先利用记录，不为套方法另做一轮研究；Agent 推测不能冒充真实买家访谈。

**资料与内容。** 内容审计先盘点现有资料，再判断准确性、用途、重复与缺口。Claim/Evidence 用来把认证、性能、交期等高风险承诺对应到证据，不要求普通说明逐句建账。图片、图纸、参数、单位、授权与适用配置都是内容的一部分；来源冲突交给事实负责人确认，不能用生成素材补造证据。需要市场或搜索研究时，再使用下方的[研究方法](#研究方法)。

**信息架构与页面。** 根据买家任务安排页面、区块和下一步动作，而不是先填满导航。分类或术语有争议时，卡片分类可帮助理解用户如何分组；已有导航难找时，树测试可检查查找路径。页面少、关系清楚时，直接检查页面地图和实际路径即可。SEO 目标影响页面主题与语言安排，但不能成为制造空页或重复页的理由。

**设计探索与定稿。** Double Diamond 提供发散、收敛与返回问题的视角，不规定工具顺序。结构、视觉方向与高保真可以相互校正；mood board 帮助表达品牌感受，Style Tiles 将其落实为字体、色彩、图片处理与界面语言。方法与工具如何服务具体判断，统一见[设计真相的方案与审查](design/设计真相.md#方案与审查)。设计成熟度取决于实际作品和取舍，不取决于生成了多少稿或经过多少工具。

**实现。** 将选定方向落实到真实内容、组件和页面，并用浏览器中的结果检查设计意图是否保留。技术底座减少重复技术工作，不替代业务判断与最终设计；原型或工具导出的代码不能直接覆盖生产实现。内容来源和实现约束从 [AGENTS 规则入口](../AGENTS.md#规则入口)进入。

**验证与上线。** 分开判断任务是否容易完成、视觉是否符合品牌，以及技术与真实交付是否成立。启发式评价能帮助发现问题，但不是目标买家测试；静态设计稿也不能证明交互、窄屏或真实询盘。工程检查见[质量门禁](质量门禁.md)，业务配置、收件与上线责任见[派生项目交接](派生项目交接.md#owner-与上线清单)，不在此复制门禁。

**反馈迭代。** 用搜索、有效询盘、销售反馈和运行问题决定下一次改动。流量少时可先看任务观察和销售反复遇到的问题，不急于做 A/B 测试，也不因短期没有订单就全面换版。事实有误补事实、找不到信息改结构、品牌表达不符调方向、实现失真修实现；只返回问题所在的环节。

## 技术底座的位置

`b2b-inquiry-site-base` 提供可复用的技术基础：默认公共页面骨架、多语言路由和 SEO 基础、询盘处理及安全边界、UI/主题入口，以及测试和 Cloudflare/OpenNext 构建部署入口。准确的当前范围由[项目](项目.md#默认能力与派生范围)维护，技术选择由[技术栈](技术栈.md)解释。

这些能力减少重复搭建与排障，不预先决定业务模型、品牌方向、页面结构或最终文案，也不提供真实服务资源、市场验证和上线收件证明。

## 拿到基础后怎么做

先按 [README 快速开始](../README.md#快速开始)运行本地页面，再结合已有业务资料和这次任务选择需要补的内容。设计阶段无需提前准备生产服务密钥。

- **复用**现有路由、语言与 SEO 能力、询盘链路、安全边界、组件、主题入口和验证工具；品牌表达可以改变，不必重建这些技术能力。
- **替换**占位品牌、页面内容和素材，选择真实语言与视觉方向；公开上线前完成域名、邮箱、法务及服务配置，具体核对[第一轮替换](派生项目交接.md#第一轮替换)。
- **新增**真实任务需要的产品、服务、关于或其他页面及内容模型。没有明确用途时，不添加目录、配置器、下载中心或额外抽象。
- **新增页面只登记一处**：在 `src/config/pages.config.ts` 的 `PUBLIC_STATIC_PAGE_DEFINITIONS` 加一条，再建 `src/app/[locale]/<路径>/page.tsx` 和各语言内容；进导航或页脚的页面还要在 messages 补文案，缺了类型检查会报错。PageType、middleware 白名单、sitemap、导航、页脚、Lighthouse 与部署 smoke 路由都从这一条推导，没登记的页面线上返回 404。动态路由（如 `/products/[slug]`）不在其中，须在 `src/middleware.ts` 白名单处另加匹配。

内容与页面由[内容规则](../.claude/rules/content.md#authoring-sources)维护；整体换肤从[主题入口](../src/app/theme.css)开始。已有设计适用时直接延续；方向不清时再探索，避免把下面的方法说明全部变成前置工作。

## 研究方法

### Full Research 与 Delta Research

- `Full Research`：进入新市场、产品或买家，法规/履约边界变化，或现有事实不足时使用；
- `Delta Research`：同一业务换地区、换语言或做小范围派生时使用，只研究变化部分。

两种模式都从当前要解决的问题开始，不因为“完整”而默认启用所有模块。

### SERP 的两次使用

第一次是 Light SERP：发现真实表达、专业词和非专业词、页面类型和研究问题。第二次是 Fixed SERP：验证搜索意图、排名页面类型、地域差异、合并/拆分和页面可进入性。Privacy、Terms、纯 Contact 或不索引的广告落地页不强制做 SERP。

### Deep Research 的研究轨道

不要提交“研究整个行业”的大 Prompt。按决策缺口选择：

```text
buyer-and-procurement
product-and-application
trust-and-standards
market-and-competition
```

Deep Research 负责外部多来源发现、比较和反证，不负责确认当前公司的供应能力、最终规格、最终 page map 或正式文案。原始报告和来源留在研究工作区，已确认内容再进入仓库；不要求固定目录名或新建研究文件。

## 内容与设计交接

交接只需让接手者理解真实内容、设计决定与仍未证明的边界，可使用现有任务或页面材料，不要求每个名称对应一份文件。外部原始研究资料按需单独保存，仓库保留实际采用的内容和决定。

### 研究包与页面地图

按任务保留业务事实、买家问题、页面关系与 CTA、适用的搜索主题和语言 URL，以及主张证据和待确认事项。需要多语言时遵循[语言与 SEO 合同](../.claude/rules/i18n.md#multilingual-url-and-seo-contract)。供应能力、公开权限和承诺由负责人确认；研究假设不能直接当作正式内容。

### 页面内容包

让设计和实现能使用实际内容：页面目标、Title/Meta、H1与区块正文、CTA和内部链接，以及适用的 FAQ、参数、图片和资料来源。注明哪些已确认、哪些仍需核实和由谁维护；无需为了凑齐字段新增无用区块。缺少素材时可以做明确标注的探索稿，不能当作真实产品或认证证据上线。

### 线框与低保真 HTML

选择足以回答当前问题的原型：草图、现有页面或低保真 HTML 均可。新结构关注阅读顺序、真实内容体量、页面与询盘路径；复用结构时检查变化即可，纯技术修复通常无需原型。结构和视觉探索可以并行，最终仍要在实际页面检查长内容、窄屏、键盘及无 JavaScript 基本阅读，不能用漂亮画面掩盖结构问题。

### Stitch/Figma

工具分工、探索稿与定稿的区别统一见[视觉候选与 AI/Figma](design/设计真相.md#视觉候选与-aifigma)。这里不另设启用顺序；工具生成结果仍需回到真实内容和仓库实现核对。

## 交接与停止

交接时说明采用了什么、为什么采用、仍不确定什么和下一步即可。方法无助于当前决定时可以不用；新增资料已不改变页面或业务决定时停止研究。已完成的判断只在新证据或相关变化出现时重开，不为保持流程运转而制造页面、报告或工具。
